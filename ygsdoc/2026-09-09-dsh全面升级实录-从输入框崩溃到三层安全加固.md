## 一、家底盘查：双仓双端口的真相

动手修任何东西之前，先花了四十分钟把"谁在跑什么"盘清楚。这台机器上 dsh 相关的运行服务有四个，长期处于"每个都能跑、但没人说得清彼此关系"的状态。

### 1.1 两个目录其实是一个仓库

`~/ygs/deepseek-harness` 和 `~/ygs/deepseek-harness-dev` 看起来像两份独立代码，实际上后者是前者的 **git worktree**：

| | master（老的） | dev（新的） |
|---|---|---|
| 目录 | `~/ygs/deepseek-harness` | `~/ygs/deepseek-harness-dev` |
| 分支 | master（0.1.1-rc.1 基线 + 157 个 fork 提交） | dev/merge-upstream-0.1.3-alpha.2 |
| 构成 | fork 独立演进 | fork 157 提交 + 上游 0.1.3-alpha.2 的 2547 个提交合并 |

dev 分支的合并是一次成功的试验：50 个冲突文件分簇解决，typecheck 0 错误、47 个受影响测试套件 1052 通过 0 失败。这个背景很重要——它决定了"3081 的代码和 3080 的官方包是同一条源码线"，后面好几处决策都建立在这个事实上。

### 1.2 四个服务、三种代码来源

| 端口 | 服务 | 代码来源 |
|---|---|---|
| 3080 | dsh web 主力（LaunchAgent `com.ygs.dsh-web` 常驻） | 官方 npm 包 `@deepseek-ai/dsh@0.1.3-alpha.2` |
| 3081 | dsh web 开发版（`dsh-web-dev.sh` 脚本管理） | dev worktree 源码构建的 `apps/cli/lib/bin.js` |
| 8490 | 微信 ygs 链 | `weclaw/dsh-openai-server.mjs` 瘦包装，复用 master 的 jsonrpc-demo 构建产物 |
| — | ygs/ygsw TUI | master 源码 tsx 直跑 |

关键的隐性耦合：3080 和 3081 **共用同一个 profile**（`~/.dsh/profiles/web`），而 profile 的依赖全部 `link:` 到 dev worktree。这意味着动 profile 等于同时动两个端口；也意味着"dev 的客户端插件产物天然是 alpha.2 兼容的"——因为 dev 就是 alpha.2 线。

另一个关键机制：3081 的前端 `apps/web/dist` 只是壳，真正的 UI 代码由 host 按模块在运行时下发各包的 `lib/client.js`。**改了 client 源码只需重建对应包的 lib 并重启，不需要重建整个前端**——这个认知让后面所有 UI 迭代的反馈回路从分钟级降到秒级。

盘查的产出是一份 ygsdoc 文档（`2026-09-08-dsh双仓双端口梳理与3081输入框修复验证.md`），把四个服务、两条源码线、一个共享 profile 的关系画成表格。这次之后的规矩是：**任何"帮梳理"类任务，产出物必须是文档，不是聊天记录**。

## 二、"without inject"崩溃侦破

### 2.1 报错锚点

栈顶三层给了三个精确锚点：`service.ts:78`、`apply.ts:323`、`InputBar.tsx:70`。定位到 dev 源码：

- `service.ts:78` 是 `packages/client/ui-model-selection` 的 `directoryFor()` 方法体内的一行：`this.ctx.remote.session`；
- `apply.ts:323` 是 `packages/client/ui-conversation` 的 `useSeatModelName` 钩子，React 渲染期调用 `directoryFor()`；
- `InputBar.tsx:70` 在渲染 composer 底栏时消费这个钩子。

### 2.2 为什么"声明了 inject 还报 without inject"

`ModelDirectoryResolver` 明明白白声明了 `static inject = ['sessions', 'remote', 'remote.session']`，按 cordis 的规则被 inject 声明的属性应该可访问。翻框架源码（`vendor/cordis/src/reflect.ts:144`）确认了抛错条件：cordis 的 caller-ctx tracker 会在服务方法被调用时，按**调用方所在 fiber 的 inject 环境**校验属性访问。服务自己声明什么没用——**关键是调用发生在谁的上下文里**。

`useSeatModelName` 是 fork 自己加的功能（commit `965053cc30`，"composer 占位符实时显示当前模型名"），它在 React 渲染路径里跨包调用另一个包的服务方法。渲染路径没有 inject 环境，于是 `this.ctx.remote.session` 被判定为"未声明的访问"，直接抛错，整个 `conversation.composer.bar` 插槽被 React 错误边界摘掉——**输入框消失**。

### 2.3 为什么 3080 不崩

官方 alpha.2 包里有**一模一样**的 `directoryFor` 代码（逐字节对比过编译产物），但 3080 稳如泰山。因为 `useSeatModelName` 是 fork 特性，上游没有人从渲染路径调 `directoryFor`——上游访问 `remote.session` 的地方都包在 `ctx.inject([...])` 回调里。同一段代码，一个调用方差异，一崩一稳。这是 fork 维护最典型的陷阱：**你 fork 的每一行新代码，都在赌它和上游的重构永远不相撞**。

### 2.4 修复与验证

正确的修法是把"运行时访问"变成"构造时捕获"：服务构造函数运行在自己的 inject 环境里，此时 `ctx.remote.session` 合法；把它存成 `this.sessionRemote`，`directoryFor` 改用捕获值。这个修复当晚由另一个并行会话落地在 dev 工作区（我的排查进行到一半时 `git status` 里多出了未提交改动——file mtime 23:18:44，比我上一次检查晚几分钟），配套加了一个用真 `Service` double 复现 caller-ctx 场景的回归测试。

我的角色变成了验证与收尾：跑该包测试套件 14 用例全过；重建产物确认 `sessionRemote` 编译进了 `lib/client.js`；重启 3081；浏览器实测——打开已有会话，占位符显示"给 deepseek-v4.1-flash-expires-on-0910 发消息"，这正是那个崩溃钩子的输出。**占位符文案本身就是修复的验收证据**，因为修复前这条路径根本活不到渲染文案。

## 三、系统管理面板：从"帮梳理"到"自己能看"

### 3.1 需求澄清

梳理完我问了方向：是加页面、加固服务托管、还是扩设置页？用户选了"3081 页面加系统管理页"——把今晚梳理出来的服务拓扑（3080/3081/8490）做成可视化管理面板。

### 3.2 架构选型：三条路的取舍

在 dev 仓库里加一个"带后端 API 的管理页"，摆着三条路：

1. **正统 RPC 路线**：host 包用 TypertRemoteService + @Remote 装饰器，client 走生成的 remote 命名空间。类型最完整，但要动 `packages/api/remotes` 的挂载清单、跑 typert 代码生成、给包加 `./typert`/`./remote` exports——改动面波及仓库公共文件。
2. **webServer 裸路由**：webhook-github 插件的路子，`ctx.webServer.register()`。但实测发现自定义路由**不走 token 信任层**（GitHub webhook 本来就必须公网可达），得自己实现鉴权，不可接受。
3. **connection.fetch.register**（file-upload 的路子）：挂在 `/api` 通道上，**信任层和 cookie 鉴权由载体统一完成**（实测裸访问 401 ✓），精确路径 + GET/POST，返回标准 Request/Response。零 typert、零协议改动、对 3080 官方 host 同样可用。

选了 3。第二层决策是**接线层级**：不动 `packages/bundle/web-app`（它随官方包发布、且 profile 共用会让改动波及 3080 的官方链路），而是让两个新包各自在 package.json 声明 `dsh.bundle.patch`（模仿 dsh-vision-router 的第三方插件模式），再在 profile 的 `dsh.profile.bundles` 数组追加包名 + dependencies 加 `link:`。这样：

- dev worktree 源码**零侵入**（全部是新增文件，不碰任何既有文件）；
- 随时可摘除（从 bundles 数组删两行）；
- 对 3080/3081 对称生效（同 profile）。

这个"爆炸半径"思维是本次最值得沉淀的架构习惯：**先决定改动影响谁，再决定改动放哪里**。

### 3.3 两个包的落地

**host 包 `@deepseek-ai/dsh-host-sysadmin`**：cordis function plugin，`inject = ['connection']`，注册四条路由——`/api/sysadmin/status`（三服务并行探测：TCP 探活 + lsof 拿 pid + ps 拿 uptime/命令行 + 版本识别【官方包读 bin 符号链接指到的 package.json，dev/weclaw 走 git rev-parse，均带 60s 缓存】+ 8490 的 `/v1/status` bearer 探测显示模型与忙碌态）、`/api/sysadmin/restart`（target 白名单校验；3080/8490 走 `launchctl kickstart -k`，3081 走 detached 子进程"先睡 1 秒再重启"——因为要重启的可能就是处理这次请求的进程，必须先应答后赴死）、`/api/sysadmin/logs`（tail，行截断 500 字符、上限 300 行）、`/api/sysadmin/urls`（从启动日志正则捞最新的 `?token=`）。状态快照带 4 秒缓存防止面板轮询打爆 lsof。

**client 包 `@deepseek-ai/dsh-client-ui-settings-sysadmin`**：通过 `ctx.slots.inject('settings.section', ...)` 注册独立顶级分区（id `sysadmin`，order 90），挂在"通用设置/模型/插件/Agent 预设"之后。数据面不搞 RPC，client 直接 `fetch('/api/sysadmin/...')` 同源带 cookie。zh 字典是 key 事实源，en 用 `satisfies` 反向校验。

### 3.4 用户反馈驱动的两次迭代

上线后用户两条反馈，各带一个教训：

**"加上 want.biz 的链接"**——第一版访问地址区只有 127.0.0.1 本机地址。补上隧道域名（dsh.want.biz → 3080、dsh-dev.want.biz → 3081，同 token），数据结构给 `SysadminUrlEntry` 加了 `label` 字段区分本机/隧道面。

**重启按钮失灵**——原生 `window.confirm` 在部分浏览器环境（自动化、内嵌 webview）会被静默吞掉，点了重启但对话框没人应答，重启永远不执行。这不只是自动化测试的问题：任何内嵌 webview 的场景都会踩。改成**面板内两段式确认**：首点按钮变红"确认重启？"，3 秒内再点才执行，超时自动解除武装。改完用 3081 自己做了一次真实重启闭环：pid 1831 → 4908，notice 文案、6 秒自动刷新全部符合预期。

教训：**确认交互不要依赖宿主环境的原生对话框**，尤其是会被 WebView 嵌入的页面。

### 3.5 验收矩阵

最终验收覆盖：4 条 API 带 cookie 全通、裸访问 401、面板三卡渲染（含 8490 的"glm-5.3-flash · 空闲"实时状态）、隧道地址渲染与打开、日志 tail（连 3080 历史上一次 EADDRINUSE 崩溃记录都完整读出）、两段式重启真实执行、3081 启动日志零 loader 失败。

## 四、构建体系的暗礁：多 agent 共享工作区

这次任务横跨 2026-09-08 深夜到 09-09 凌晨，期间**至少两个 agent 会话在同一个 dev worktree 里工作**。由此产生了今晚最烧脑的三段排障。

### 4.1 composite 工程图的连锁反应

给 host 包写 tsconfig 时，最初模仿仓库惯例 `extends tsconfig.base.json + references`。结果 `tsc -b` 顺着 references 把 vendor/schemastery 也拉进重建，然后在一堆 `exactOptionalPropertyTypes` 严格性错误上爆炸——而仓库全量构建明明是绿的。根因：tsconfig.base.json 的 `paths` 把包名映射到**源码目录**（"Project references, not declaration path aliases"），任何非根工程图的包一旦被引用链扫到，就会用根的严格度去编 vendor 源码。

解法：**profile 级插件彻底脱离仓库 composite 工程图**。host 包用独立宽松 tsconfig（`paths` 直指上游已构建的 `lib/types/*.d.ts` + `tsc --noEmit`），tsdown 直接从 src 打包；client 包因为必须用仓库的 `clientBundle` 产出浏览器半（带 `window.__ModuleLoader__` 横幅和 CSS Modules 内联），保留标准结构但裁剪 references。规则：**不属于根工程图成员的包，就不要假装自己是**。

### 4.2 我的 cd 事故

排查中两次因为 shell 工作目录残留跑错命令：一次在仓库根跑了 `pnpm run build`，意外触发全量构建（结果歪打正着验证了全量绿）；一次 `ls lib/` 在根目录下找出了乌龙结论。多命令链里的 `cd` 是万恶之源，**长命令一律绝对路径 + 每步回显 pwd**。

### 4.3 产物被并行构建覆盖

token 钩子改完后，`build:lib:host` 明明验证过产物里有 `DSH_WEB_TOKEN`，几分钟后重启 3081 却发现行为随机——产物里 grep 变 0。翻时间线：另一个会话在期间提交了三个 ui-chat 修复并跑了它自己的构建流程，把 connection 包的产物用**旧的 tsc 缓存输出**重新打包覆盖了。

这里挖出一个构建矩阵盲区：connection 这类 dual-face 包的 node 半（`lib/index.js`）归 **client face**（clientBundle）构建——host face 的 workspace tsdown 对它返回 `SKIP_WORKSPACE_BUILD`。所以"改了 connection 源码"的正确重建姿势是包目录下 `tsdown --env.DSH_BUILD_FACE client`，而不是全量 host build。这条已写进文档，多 agent 共享工作区时，**每个人的构建都可能抹掉别人的产物，源码在磁盘上就有最终解释权——冲突后重新构建即可收敛**。

## 五、token 持久化：手机登录的最后一公里

### 5.1 鉴权机制拆解

alpha.2 的 web 鉴权分两层。**cookie 签名密钥**持久化在 credentials 存储（`~/.dsh/.credentials.yaml`），cookie 有效期 30 天且按访问域名（authority）分别签发——这层本来就不丢。**启动 token**（URL 里 `?token=` 换 cookie 的那个）则在 `processLaunchToken()` 里每次启动 `randomBytes(32)` 纯随机，而且翻遍源码没有任何 env/配置钩子。每次重启，所有旧 token 链接作废；桌面端有脚本自动开浏览器，手机走隧道域名的人只能在 Mac 上翻日志、再想办法把 43 位随机串弄到手机上——"非常不便"四个字就是这么来的。

### 5.2 钩子设计

dev 源码 `processLaunchToken` 加了环境变量支持：`DSH_WEB_TOKEN` 若匹配 `^[A-Za-z0-9_-]{32,}$`（base64url、128 位强度）则固定使用；未设置照旧随机；**格式非法打 warn 并回退随机**——绝不因为一个配错的弱 token 静默降低安全水位。

### 5.3 两个实例的两条路

- **3081（dev 构建）**：`dsh-web-dev.sh` 新增 `ensure_token`——首次启动生成 token 文件 `~/.dsh/run/dsh-web-dev.token`（0600），此后每次启动 `export DSH_WEB_TOKEN`。轮换 = 删文件重启。
- **3080（官方 npm 包）**：官方产物没有钩子，按这台机器已有惯例（`patch-runtime-alias.sh`、各种 `.bak` 备份）写了幂等热修脚本 `~/.dsh/patch-web-token.sh`：对编译产物 `dsh-client-connection/lib/index.js` 的 `processLaunchToken` 做锚点文本替换注入同款 env 判断，备份 `.bak-web-token`，**全局包升级会冲掉补丁、重跑脚本即恢复**；未打补丁时 env 被忽略、自动降级回随机 token——失败模式是安全的。token 本体放在 LaunchAgent plist 的 `EnvironmentVariables`（`plutil -replace` 写入，lint 通过）。

### 5.4 一个采样时序陷阱

第一次验证"重启后 token 不变"时得到了假阳性：两次读日志值相同。真相是 token 行是服务 boot 后**异步写入**日志的，脚本等端口就绪就返回了，grep 到的还是上一轮的旧值。第二次验证改成 restart 后 sleep 3 再采样，立刻现出原形（三次 boot 三个随机 token）。**对异步写日志的系统做断言，必须等写入完成**——这条和"看清调用方上下文"一样，属于今晚最值钱的两条调试教训。

### 5.5 最终验证

3081：连续两次重启 token 均等于 token 文件值 ✓；正确 token → 303 下发 cookie → 带 cookie 200；错误 token → 401 ✓。3080：launchctl kickstart 跨重启 token 不变 ✓。至此手机可以收藏固定链接永久使用。

## 六、安全收口：Cloudflare Access 补齐最后一块

token 固定之后自然引出安全问题："token 在链接里，公共 WiFi 下是否不太安全？要不要套 Cloudflare Access？"

实测给出了三个事实。第一，**公共 WiFi 嗅探是伪威胁**：token 全程 HTTPS，WiFi 侧只能看到密文。URL 带 token 的真实风险面是浏览器历史/云同步、截图分享、代理与日志留存——"链接泄露"级别而非"网络窃听"级别。第二，**真正的威胁模型是暴露面**：这个服务背后是能执行 shell、读写文件的完整 coding agent，"知道链接即可用"的单因子模型意味着链接从任何渠道泄露（聊天记录、同步相册、截屏）都等于交出机器 shell。第三，实测发现 **dsh.want.biz（3080）早就套了 Cloudflare Access**（裸访问 302 跳 `yuanguangshan.cloudflareaccess.com`），唯独 dsh-dev.want.biz（3081）裸奔。

结论水到渠成：给 dsh-dev 补上同款 Access。机器上没有存 Cloudflare API Token（翻了 `.cloudflared`、shell 配置、auth 文件），正准备引导用户建 token 时，用户自己在 Zero Trust 控制台把应用加好了。实测确认：裸访问 302 进 Access 登录页 ✓；**带 token 访问也被 Access 拦截，且回跳地址完整保留了 token**（`redirect_url=%2F%3Ftoken%3D...`）——Access 认证完成后自动带 token 完成第二道验证，登录链路不断 ✓。

最终形成三层防护：**Cloudflare Access（身份层：谁能到门口）→ 固定 token（第二道门）→ HttpOnly + SameSite=Strict 30 天 cookie（会话层）**。用户侧体验：手机收藏带 token 的链接，第一次过一遍 Access 验证码，之后点收藏即进；Access 会话过期也只是重收一次验证码，token 永远不需要手输。

## 七、方法论沉淀

**多 agent 协作纪律**：共享 worktree 上开工前先 `git status` + 关键文件 mtime；发现并行改动时明确分工（今晚的分工天然合理——对方修崩溃、我验证收尾再做增量功能）；每个会话的产出写独立 ygsdoc 文档，冲突后以源码为准重新构建。

**调试心法两条**：一是"看清调用方上下文"——cordis 的 inject 校验、React 的渲染环境、原生对话框的宿主差异，所有"声明了却无效"的问题最终都指向**代码运行在谁的环境里**；二是"异步系统的断言必须等写入完成"，假阳性比失败更误导。

**架构习惯一条**：先算爆炸半径再选改动位置。系统管理面板本可以走最"正统"的仓库级接线，但 profile 层方案用新增文件实现同等功能、对两个 host 对称、随时可摘——在个人基础设施上，可摘除性比正统性值钱。

**安全心智模型一条**：评估暴露面时别盯着"传输是否加密"（HTTPS 时代这基本是送的），要问"这一层保护被绕过后，攻击者能拿到什么"。token 泄露 = shell，这才是要加 Access 的原因。
