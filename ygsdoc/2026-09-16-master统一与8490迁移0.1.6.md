## 四、附带修复（同一根因）

### 4.1 REPL 的运行时死路径

`apps/repl/src/core.ts` 的 `runtimeBin()` 默认值仍指向 0.1.5-rc.2 起就已不存在的 `packages/examples/jsonrpc-demo/lib/bin.js`，`interactiveConfig()` 同理。测试只断言**路径字符串正则**、不校验文件存在，所以 typecheck 与测试都没拦住——**dev 线上 REPL 一直是起不来的**（早于本次 0.1.6 升级，非本次引入）。

修复：
- `core.ts`：`dshRuntimeLaunch()` / `profilePatch()` 取代 `runtimeBin()` / `interactiveConfig()`（`DSH_REPL_DSH_BIN` / `DSH_REPL_PROFILE` / `DSH_REPL_PATCH`，兼容旧 `DSH_REPL_RUNTIME`）
- `tui-repl.ts`：改用 SDK 的 `resolveDshLaunch()` 构造 `RuntimeProcessOptions`
- `doctor.ts`：运行时检查改按 dsh CLI + profile patch 判定
- `packages/sdk/client/src/index.ts`：导出 `resolveDshLaunch` / `RuntimeProcessOptions`

### 4.2 `repoRoot()` 在构建产物下错位

`core.ts` 用 `dirname` 数 4 层推导仓库根：源码在 `<root>/apps/repl/src/` 正确，但构建产物在 `lib/bin.js`（bundle）或 `lib/types/core.js`（逐模块），深 1–2 层，会解析成 `<root>/apps`，`dshBin` 变成 `apps/apps/cli/lib/bin.js`。改为**向上找 `pnpm-workspace.yaml`**，保留旧算法作兜底。

实测（构建产物）：`repoRoot = /Users/ygs/ygs/deepseek-harness-dev`、`dshBin exists: true`、`patch exists: true`。

### 4.3 last-model 无效值

`~/.dsh/last-model.json` 出现 `provider:"other", model:"other"`（不在任何 providers 表内），8490 启动时会原样采用 → runtime 报 `no adapter registered for provider`。已加校验：不在表内则回退，并打印忽略原因。来源未定位（写入时间点与跑测试重合，但相关测试都有 `DSH_REPL_LAST_MODEL_FILE` 隔离），**待观察是否复现**。

### 4.4 8490 默认路由

`cc-switch`（127.0.0.1:15721）当前未常驻，而链路实际一直用 `tencent`（wb-proxy 8487）。已在 LaunchAgent `com.ygs.dsh-proxy` 加 `DSH_REPL_PROVIDER=tencent` / `DSH_REPL_MODEL=deepseek-v4-flash` 作为 last-model 无效时的回退。

### 4.5 master worktree 重建（含一个 fork 构建缺口）

master 统一后 `node_modules` 其实已是 0.1.6（pnpm store 共享，state 文件与锁文件 md5 一致），失败的是 **`lib/` 里的 0.1.1 残留**：

1. `pnpm run clean` 清掉 306 个残留路径（17 个已被上游删除的包，含 `packages/examples/jsonrpc-demo`——**master 上那个老 8490 链路一直跑的就是这份残留产物**）。
2. 再构建仍失败：`UNRESOLVED_ENTRY: Cannot resolve entry module lib/types/index.js`。
3. 定位：`packages/client/ui-settings-sysadmin` 的 tsdown 入口是 `lib/types/index.js`，但该包**既不在 `tsconfig.client.json` 的 references 里，也没有 composite 配置**——没有任何步骤会产出这两个文件；本机一直靠 9 月 9 号手工构建的残留撑着。`host/sysadmin` 不受影响（它刻意从 `src/index.ts` 直接打包）。
4. 修复（commit `a6fbc20ce8`）：包 tsconfig 改为 client 面惯例（`extends tsconfig.base.client.json` + `rootDir/outDir` + `references`，去掉手写 `paths`），并在 `tsconfig.client.json` 登记该引用。
5. 复验：master `clean` + `build`(**exit 0**) + `typecheck`(**exit 0**)，产物齐全。

顺带：dev 也有 8 个已删包的 `lib` 残留（构建报 244 个产物 vs master 242），定向清理后两边**同为 242**。

> 这是个真实的 fork 构建缺口：**修好之前，任何一次 `pnpm run clean` 都会让构建彻底起不来**，dev 只是靠残留文件侥幸可用。

### 4.6 `ygs` / `ygsw` 两个快捷方式报错的两个根因

现象：

```
ygs  → 初始化失败: initialize timed out after 10000ms waiting for dsh profile "ygs"
ygsw → 初始化失败: dsh profile "ygs": Cannot find module '.../deepseek-harness/apps/cli/lib/bin.js'
```

**根因一（ygsw 的 MODULE_NOT_FOUND）**：两个快捷方式都从**主仓**启动（`ygs()` 里
`cd /Users/ygs/ygs/deepseek-harness`；`launch-tui.sh` 的 `REPL_ROOT` 是脚本自身目录），
用的是主仓的 `apps/cli/lib/bin.js`——而那次报错正好撞在 §4.5 的 `clean`+重建窗口里，
文件被清掉还没生成。

**根因二（ygs 的超时，真正的坑）**：`~/.zshrc` 里 `DSH_REPL_PROVIDER="xiaomi"`，
但 **ygs profile 里没有 `xiaomi` 这个 route**（2026-09-09 从 cc-switch 拆出直连时已
并入 `opencode-go`）。已复现：`provider=xiaomi` → 必现上面那条超时；改成
`opencode-go` → `turn/end={"kind":"completed"}`。

**为什么报的是"超时"而不是"provider 不存在"**：fork 给 SDK server 加的
`waitForProvider` 原等 **15s**，而 SDK 客户端的 initialize 握手只有 **10s**——
客户端先超时，服务端那句确定性的 `no adapter registered for provider "xiaomi"`
永远来不及返回。凡 ≥ 客户端上限的服务端等待都是死代码，已降到 **8s**（`eb06987d4e`）。
修后同样场景报错变成：

```
FAIL no adapter registered for provider "xiaomi"
```

处置：`.zshrc` 的 provider 改为 `opencode-go`；服务端等待上限降到 8s；两仓同步重建。

验证：`ygs` 实跑（tsx 源码入口）与 `ygsw` 实跑（`apps/repl/lib/bin.js` 构建产物）
均 `初始化失败 = 0` / `MODULE_NOT_FOUND = 0`，TUI 头部显示 `ygs · opencode-go / mimo-v2.5`。
